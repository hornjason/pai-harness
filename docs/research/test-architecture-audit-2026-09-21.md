# Test Architecture Audit — 2026-09-21

## Finding

70% of test logic bypasses the conformity engine deep module.

## Three Test Layers

| Layer | File(s) | Lines | Config-driven? | Role |
|---|---|---|---|---|
| Hand-written phase tests | phase-0/1/2/3/4/5.test.ts | 2,657 | ❌ Manual | SC IDs copy-pasted, assertions hand-coded |
| Conformity engine | lib/conformity.ts → scaffold-conformity.test.ts | ~400 + 9 | ✅ Yes | Reads SCs from specs, auto-generates assertions via matchPattern() |
| Spec-compliance auto | spec-compliance-auto.test.ts | 64 | ✅ Partial | Generated by sync-spec-tests.ts, can go stale |

## What Happens When You Add an SC

| Step | Conformity Engine | Phase Tests | Golden Fixture |
|---|---|---|---|
| SC added to spec | Auto-discovered ✅ | Nothing ❌ | Nothing ❌ |
| Test generated | If matchPattern() recognizes wording ✅ | Human writes manually ❌ | No staleness check ❌ |
| Fixture needs update | No check ❌ | No check ❌ | No check ❌ |

## Duplication

Phase-0 alone has 149 SC references across 949 hand-written lines. Many duplicate what matchPattern() handles. Example: phase-0 manually checks `existsSync(join(OUTPUT, ".git"))` for SC-97, but the conformity engine's "exists" matcher does the same thing from SC text automatically.

## Deep Module vs Thin Consumer

- **Deep module:** `lib/conformity.ts` — parses specs, runs matchers, manages findings, exports `runScaffoldConformity()`
- **Ideal thin consumer:** `scaffold-conformity.test.ts` — 9 lines, just calls the engine
- **Fat consumers:** phase-0/1/2/3/4/5.test.ts — 2,657 lines bypassing the engine entirely

## Recommended Architecture

```
spec file (SC definitions)
    ↓ conformity engine reads SCs
    ↓ matchPattern() generates assertion OR flags "needs custom matcher"
    ↓ assertion runs against golden fixture output
    ↓ missing fixture content = RED test (staleness check)
    ↓ update fixture → GREEN
    ↓ sync-sc-status.ts flips checkbox
    ↓ pre-commit updates PROJECT-STATE.md
```

Phase tests become thin consumers:
```typescript
// phase-0.test.ts — target state
import { runScaffoldConformity } from "../lib/conformity";
const PHASE_0_SCS = ["SC-1", "SC-2", "SC-3", ...]; // or derive from spec
runScaffoldConformity(OUTPUT, { filter: PHASE_0_SCS });
```

## Migration Strategy

1. Serena writes ADR with approach
2. One phase at a time: start with phase-0 (largest, 949 lines)
3. For each hand-written test, check if matchPattern() already handles it — if yes, delete
4. For tests needing custom logic, add a new matcher to matchPattern()
5. Add fixture staleness check: scan SCs for file/dir references, verify fixture has them
6. Phase test shrinks to thin consumer calling the engine with a phase filter

## Risk

If we don't do this before Phase 2, every new SC requires:
- Adding to spec (correct)
- Writing a hand-wired test (wrong — should be auto-generated)
- Updating fixture (no signal tells you to)

Phase 2 has ~30 SCs. That's 30 hand-written tests on the wrong architecture.
